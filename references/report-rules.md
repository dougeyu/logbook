# 报告规则

## 证据分级

使用可获得的最高等级证据,并保留其局限。

- `verified`(已验证):直接的任务记录、提交元数据、测试输出、部署记录或其他可观察的凭证。
- `user_confirmed`(用户确认):用户明确陈述的事实。可用于起草,但不得暗示经过独立核实。
- `inferred`(推断):证据未直接确立的合理推测。除非明确标注,否则不得进入最终表述。

除非用户要求审计追踪,否则不对外暴露这些内部标签。

## 状态判定

- `completed`(已完成):必须有可观察的结果 + 至少一条证据。只做了动作不算完成。
- `in_progress`(进行中):已开始但预期结果尚未完成。有依据的进度数字按原样保留。
- `blocked`(阻塞):因明确的依赖、决策、权限、资源或缺陷无法继续推进。写明阻塞原因;知道下一步动作时一并写出。
- `planned`(计划):尚未开始。只能表述为"打算做",绝不能写成已取得的成果。
- `unverified`(未核实):说法可能相关但证据不足。先追问确认,或从正式报告中省略。

证据与声称的状态冲突时,采用确定性更低的状态,并把分歧暴露给用户。

## 去重

仅当多条记录指向同一目标且描述同一成果时才合并。合并时汇总各自的证据,保留最新的有依据状态。不因为措辞相似就合并不同的缺陷、客户、交付物或里程碑。

## 追问策略

每轮最多 3 个问题。按此优先级:

1. 声称的结果是否真的完成且可观察?
2. 未完成事项卡在哪里?
3. 下一个具体动作、负责人或截止时间是什么?

不会改变报告内容的细节不问。用户表示无法补充时立即停止追问,用"未核实"标注。

## 隐私与权限

- 只收集完成报告所需的最少信息。
- 元数据足够时,不读文件内容。
- 默认不申请管理员、全邮箱、全仓库或全组织级权限。
- 对令牌、凭据、个人身份信息、内部链接、客户机密、不必要的绝对路径进行脱敏。
- 发送、发布或修改外部系统之前,必须当场取得用户确认。

## 语言质量

- 跟随用户的语言和职场语气。
- 短句优先,名词具体,动词精确。
- 事实、计划、风险分开写。
- 不写空洞的表扬、夸大的影响和无依据的因果。
- 数字只有来源明确时才保留。

## 自然写作规范(去 AI 味)

报告应当读起来像人写的,不像 AI 生成的。以下模式必须避免:

### 禁止的格式习惯

| 禁止 | 原因 | 替代做法 |
| --- | --- | --- |
| `**加粗关键词**` (纯文本场景) | 典型 AI 格式化习惯,真人不这么写纯文本 | 用标题层级区分,或直接写不装饰 |
| `——` 长破折号连接因果 | AI 爱用破折号解释,真人更习惯句号断开 | 拆成两句,或用逗号 |
| `首先…其次…最后…` 排比结构 | 机械感强,像教科书不像工作汇报 | 直接列举,不加序号前缀 |
| `此外`、`另外`、`值得一提的是` 过渡词 | 书面气太重,日报不需要 | 另起一段直接说 |

### 禁止的用词

| 禁止 | 原因 | 替代 |
| --- | --- | --- |
| `显著提升` | 没有数字支撑的形容词等于没写 | 写具体数字,或改成"提升"不加修饰 |
| `积极推进` | "积极"是态度,不是结果 | 写做了什么动作 |
| `圆满完成` | 汇报不是颁奖词 | 写"完成",有成果写成果 |
| `深入理解`、`认真学习` | 无法验证的主观感受 | 写具体学到了什么,能拿来做什么 |
| `赋能`、`抓手`、`闭环`、`对齐` | 互联网黑话,空洞 | 用日常语言说清楚在做什么 |
| `一定程度上`、`相对而言` | 模糊限定,逃避精确 | 删掉,或改成具体范围 |

### 提倡的写法

- **短句**。一句话一个意思,超过 40 字就拆。
- **主动语态**。"修了一个 bug"比"一个 bug 被修复了"更像人话。
- **具体名词**。"改了下单页面的支付按钮样式"比"优化了前端交互体验"好一百倍。
- **允许不完美**。真人的日报偶有口语、偶有停顿;不需要每句都工整对称。
- **可加一句感受**。如果给同事或自己看,写一句"这个坑查了大半天,结果是配置少了个逗号"比干巴巴的"排查配置问题"更有信息量。
